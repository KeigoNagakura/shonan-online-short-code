# ブランチ運用仕様

> 文書整理日: 2026-09-27。既存本文を保持し、日本語名・分類・参照リンクを整理。ファイル名の日付は本文の作成・実施日を優先し、不明なものは整理日とした。 以下は移設前からの運用方針・計画。旧docker/・CI資材や外部設定の適用状態は未確認。現在の起動は[Docker開発環境](Docker開発環境_20260927.md)を参照。

> 第2版。最終更新日: 2026-11-10。更新配信の同一ホスト制約とGit連動ワークフローを反映。

## 1. 目的

この文書は、WordPressプラグイン `ShonanOnlineShortCode` の開発、検証、リリース、緊急修正を安全に進めるためのGit運用ルールを定義します。

このプロジェクトでは `develop` ブランチを使用しません。常に最新の `main` から作業ブランチを作成し、GitHubのPull Requestで `main` に戻すGitHub Flow型で運用します。

## 2. 基本原則

```text
main
 └─ feature/*、fix/*、docs/*、release/*、hotfix/*
       └─ Pull Request → main
```

- `main` は常に動作可能な状態を維持します。
- すべての作業ブランチは最新の `main` から作成します。
- すべての変更はPull Requestを経由して `main` に戻します。
- `main` への直接pushは禁止します。
- マージ済みの作業ブランチは削除します。
- リリース時は `main` のリリースコミットへタグを付けます。

## 3. ブランチ構成

| ブランチ | 用途 | 作成元 | マージ先 |
| --- | --- | --- | --- |
| `main` | リリース済みかつ次の作業基準 | ― | ― |
| `feature/*` | 機能追加・改善 | `main` | `main` |
| `fix/*` | 通常の不具合修正 | `main` | `main` |
| `perf/*` | 性能改善 | `main` | `main` |
| `docs/*` | ドキュメントのみの変更 | `main` | `main` |
| `release/*` | バージョン確定とリリース準備 | `main` | `main` |
| `hotfix/*` | 公開中バージョンの緊急修正 | `main` | `main` |

### 3.1 `main`

- 常にDocker環境で起動できる状態を維持します。
- 公開可能な品質を維持します。
- Pull Requestを経由して更新します。
- リリースコミットには `v3.7.0` のようなタグを付けます。
- force pushや履歴の書換えは原則禁止します。

### 3.2 作業ブランチ

- 1ブランチ1目的にします。
- 作業開始時の最新 `main` から作成します。
- 長期間放置せず、小さな単位でPull Requestを作成します。
- マージ前に最新 `main` を取り込みます。
- マージ後はローカルとGitHubの両方から削除します。

## 4. ブランチ命名規則

英小文字、数字、ハイフンを使用します。GitHub Issueがある場合はIssue番号を含めます。

```text
feature/issue-123-add-countdown-option
fix/issue-124-escape-shortcode-output
docs/update-setup-guide
release/3.7.0
hotfix/3.6.3-update-endpoint
```

避ける例：

```text
test
fix
work
nagakura-branch
new-branch
```

## 5. GitHub設定

`main` にブランチ保護を設定します。

このプロジェクトでGitHub上に設定する項目は次の2点です。

- CIの全必須チェックが成功していることを `main` へのマージ条件にする
- マージ済みの作業ブランチを自動削除する

具体的な設定手順と必須チェック名は [GitHubリポジトリ設定](GitHubリポジトリ設定_20260927.md) を参照してください。

デフォルトブランチは `main` とします。

## 6. 通常開発フロー

### 6.1 作業開始

ローカルの変更が残っていないことを確認し、最新の `main` からブランチを作成します。

```powershell
git status
git switch main
powershell -NoProfile -ExecutionPolicy Bypass -File .\docker\update-project.ps1
git switch -c feature/issue-123-add-countdown-option
```

不具合修正の場合：

```powershell
git switch main
powershell -NoProfile -ExecutionPolicy Bypass -File .\docker\update-project.ps1
git switch -c fix/issue-124-escape-shortcode-output
```

### 6.2 開発環境起動

```powershell
powershell -ExecutionPolicy Bypass -File .\docker\setup.ps1
```

通常のプラグイン開発は `src/so-short-code` 配下で行います。変更はコンテナへ直接反映され、PHPのOPcacheは最大約2秒で更新を再確認します。

### 6.3 コミット

```powershell
git add src/so-short-code
git commit -m "feat: add countdown display option"
```

### 6.4 作業ブランチをpush

push前に現在の開発DBをダンプし、隔離DBへの復元検証を行います。SQLに差分がある場合はpush対象のコミットへ含めます。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\docker\export-database.ps1
git add db/init/wordpress.sql
git commit -m "chore: update development database"
```

SQLに差分がない場合、DB用コミットは不要です。ただしダンプ・復元検証自体は省略しません。

```powershell
git push -u origin feature/issue-123-add-countdown-option
```

GitHubで作業ブランチから `main` へのPull Requestを作成します。

### 6.5 `main` の最新化

Pull Requestのマージ前に `main` が更新されていた場合は、作業ブランチへ取り込みます。

```powershell
git fetch origin
git rebase origin/main
git push --force-with-lease
```

共有作業中など、rebaseで履歴を書き換えたくない場合はマージします。

```powershell
git fetch origin
git merge origin/main
git push
```

`--force` は使用せず、rebase後に必要な場合だけ `--force-with-lease` を使用します。

### 6.6 マージ後

```powershell
git switch main
powershell -NoProfile -ExecutionPolicy Bypass -File .\docker\update-project.ps1
git branch -d feature/issue-123-add-countdown-option
```

## 7. コミットメッセージ

Conventional Commits形式を使用します。

| 種別 | 用途 | 例 |
| --- | --- | --- |
| `feat` | 機能追加 | `feat: add shortcode preview` |
| `fix` | 不具合修正 | `fix: escape shortcode attributes` |
| `refactor` | 挙動を変えない整理 | `refactor: split update checker` |
| `perf` | 性能改善 | `perf: cache shortcode output` |
| `docs` | 文書のみ | `docs: update release procedure` |
| `test` | テスト | `test: add shortcode rendering tests` |
| `build` | ビルドや依存関係 | `build: update PHP image` |
| `ci` | CI設定 | `ci: add plugin syntax check` |
| `chore` | その他の保守 | `chore: update development data` |

ルール：

- 1行目は簡潔な命令形にします。
- 1コミット1目的にします。
- `fix stuff`、`update`、`test` だけの曖昧なメッセージは使用しません。
- 互換性を壊す変更は本文へ `BREAKING CHANGE:` を記載します。

## 8. Pull Request

Pull Requestには以下を記載します。

```markdown
## 変更内容

- 何を変更したか

## 理由

- なぜ必要か

## 確認方法

1. 実行した手順
2. 確認した画面やショートコード

## 影響範囲

- WordPress管理画面
- フロント表示
- DB変更の有無

## 関連Issue

- Closes #123
```

レビューでは以下を確認します。

- PHPエラー、Warning、Noticeが発生しない
- 入力値の検証と出力時のエスケープが適切
- nonceと権限確認が必要な処理に実装されている
- SQLを直接扱う場合はプリペアドステートメントを使用
- 既存ショートコードの互換性を壊していない
- 外部APIキー、パスワード、個人情報を追加していない
- 不要な生成ファイルやログを追加していない
- Docker環境を壊していない

## 9. マージ方式

通常のPull Requestは `Squash and merge` を使用します。

```text
作業ブランチ → Pull Request → Squash and merge → main
```

これにより、作業中の細かなコミットを1つにまとめ、`main` の履歴を読みやすく保ちます。

例外として、複数の独立したコミットを残す必要がある大規模変更では `Create a merge commit` を使用できます。使用理由をPull Requestへ記載します。

## 10. バージョニング

バージョンは `MAJOR.MINOR.PATCH` 形式を使用します。

```text
3.7.0
```

| 部分 | 更新条件 |
| --- | --- |
| `MAJOR` | 後方互換性を壊す変更 |
| `MINOR` | 後方互換性のある機能追加 |
| `PATCH` | 後方互換性のある不具合修正 |

WordPressプラグインの更新判定に使うため、リリース時は以下を必ず一致させます。

| ファイル | 更新箇所 |
| --- | --- |
| `src/so-short-code/so_short_code.php` | `Version:` |
| `src/so-short-code/settings.php` | `SOSC_VERSION` |
| `src/so-short-code/settings.php` | `SOSC_CSS_JS_TIME` |
| `src/so-short-code/settings.php` | `CHANGELOG` |
| `src/so-short-code/update/so-short-code.json` | `version` |
| `src/so-short-code/update/so-short-code.json` | `download_url` |
| `src/so-short-code/update/so-short-code.json` | `sha256`（完成した配布ZIPのSHA-256） |
| `src/so-short-code/update/so-short-code.json` | `last_updated` |

`Version:`、`SOSC_VERSION`、JSONの `version` が一致しない状態ではリリースしません。

コードと更新判定には `3.6.2` のようなSemVer形式を使用します。配布ZIPはディレクトリ一覧で並びやすくするため、`so-short-code-03.06.02.zip` のような2桁ゼロ埋め形式を使用します。例えば `3.10.4` は `03.10.04` とします。

### 10.1 更新配信先の移行予定

現在の更新配信先は `api.shonan-online.com` です。次回リリースから `sosys.shonan-online.com` へ変更する予定です。旧版は旧ホストのJSONとZIPを必要とするため、旧ホストは利用状況と実機更新試験を確認して廃止判断するまで維持します。

切替対象リリースが確定するまでは、現在のURLを維持します。切替時は次の項目を同一リリースで揃えます。

- `src/so-short-code/settings.php` の `SOSC_API_URL`
- `src/so-short-code/update/so-short-code.json` の `download_url`
- `sosys.shonan-online.com` 上の更新JSON
- `sosys.shonan-online.com` 上の配布ZIP
- HTTPS証明書、アクセス権、外部からの到達性
- 既存プラグインからの更新検出とZIP取得

既存バージョンは旧URLしか参照できず、JSON取得元とZIPのホスト一致も検証します。旧ホストではJSONと同じホストのZIPを継続配信します。新URLへのリダイレクトだけでは旧版の更新互換性を保証できません。

## 11. リリースフロー

以下は `3.7.0` をリリースする例です。

### 11.1 リリースブランチ作成

```powershell
git switch main
powershell -NoProfile -ExecutionPolicy Bypass -File .\docker\update-project.ps1
git switch -c release/3.7.0
```

### 11.2 リリース情報更新

「10. バージョニング」に記載した全ファイルを更新します。リリースブランチでは新機能を追加せず、バージョン、更新履歴、リリース上の不具合だけを修正します。

```powershell
git add src/so-short-code
git commit -m "chore: prepare release 3.7.0"
git push -u origin release/3.7.0
```

### 11.3 リリース確認

最低限、以下を確認します。

1. Docker環境を初期状態から構築できる
2. WordPress管理画面でプラグインを有効化できる
3. PHPエラーが発生しない
4. 主要ショートコードが期待どおり表示される
5. 管理画面の保存処理が正常に動作する
6. バージョン情報が全ファイルで一致する
7. 更新JSONが有効なJSONである
8. `docker/build-release-package.ps1` がZIPを生成し、更新JSONのSHA-256を自動更新・検証できる
9. 配布ZIPの展開先が `so-short-code` になる
10. SWELL、Twenty Twenty-Five、Welcart、Contact Form 7、Chrome、Edge、Safari、iPhone Safari、Android Chromeの担当者・確認日・結果がPull Requestに記録されている
11. 配信先移行リリースでは、コード、更新JSON、ZIPの公開先がすべて `sosys.shonan-online.com` で一致する

10の未確認項目が1件でもある場合、正式リリースへ進みません。有償資産と実機は正規に用意された検証環境を使用します。

### 11.4 Pull Requestとタグ

1. `release/3.7.0` から `main` へのPull Requestを作成
2. レビューと動作確認後にマージ
3. 最新の `main` を取得
4. リリースタグを作成してpush

```powershell
git switch main
powershell -NoProfile -ExecutionPolicy Bypass -File .\docker\update-project.ps1
git tag -a v3.7.0 -m "Release 3.7.0"
git push origin v3.7.0
```

GitHub Releaseと配布ZIPを作成し、更新JSONで指定したURLへ公開します。完了後、`release/3.7.0` を削除します。

## 12. 緊急修正フロー

公開中の `3.7.0` を `3.7.1` へ緊急修正する例です。

```powershell
git switch main
powershell -NoProfile -ExecutionPolicy Bypass -File .\docker\update-project.ps1
git switch -c hotfix/3.7.1-update-endpoint
```

修正とバージョン更新を行います。

```powershell
git add src/so-short-code
git commit -m "fix: correct update endpoint validation"
git push -u origin hotfix/3.7.1-update-endpoint
```

その後の流れ：

1. `hotfix/*` から `main` へのPull Requestを作成
2. レビューと動作確認後にマージ
3. `main` に `v3.7.1` タグを作成してpush
4. 配布ZIPと更新JSONを公開
5. hotfixブランチを削除

## 13. Docker・DB変更

Docker関連の変更も最新の `main` から作業ブランチを作成します。

```text
feature/update-php-version
feature/improve-local-https
perf/improve-docker-filesystem
```

Pull Requestでは少なくとも以下を確認します。

```powershell
docker compose -f docker\compose.yml config --quiet
powershell -ExecutionPolicy Bypass -File .\docker\setup.ps1
```

DB初期データのルール：

- MySQLの `/var/lib/mysql` はGit管理しません。
- 共有するDBは `db/init/*.sql` として管理します。
- SQLには本番データ、不要な個人情報、APIキーを含めません。
- SQL変更はPull Requestの説明に影響内容を記載します。
- SQLを更新した場合、空のボリュームから自動投入できることを確認します。
- push前は変更種別にかかわらず `docker/export-database.ps1` を実行し、現在DBを検証済みSQLとして保存します。
- 最新版の取得には `docker/update-project.ps1` を使用し、Git版SQLでローカルDBを置換します。
- 有効な外部プラグインは `docker/required-plugins.json` に固定し、別PCでも同じ本体とバージョンを自動導入できる状態にします。

```powershell
docker compose -f docker\compose.yml down --volumes --remove-orphans
powershell -ExecutionPolicy Bypass -File .\docker\setup.ps1
```

この確認はローカルDBを削除するため、必要なデータを事前にバックアップします。

## 14. Git管理しないもの

- `site/wp-content/uploads/`
- `docker/localhost.crt`
- `docker/local-dev-ca.crt`
- CA秘密鍵、TLS秘密鍵
- MySQLの実データファイル
- ログ、キャッシュ、一時ファイル
- 本番APIキー、アクセストークン、本番パスワード
- 個人情報を含むSQLやファイル

`docker/.env` と `site/wp-config.php` はローカル開発用の固定デモ情報として意図的にGit管理します。本番用の値は記載しません。

## 15. 禁止事項

- `main` への直接push
- `main` へのforce push
- レビューなしでの自己マージ
- 最新の `main` を基準にしないブランチ作成
- 複数の無関係な変更を1つのPull Requestへ含めること
- バージョン不一致のままリリース
- 本番秘密情報や個人情報のコミット
- Docker全体を対象にした一括削除
- リリースタグの付け替えや再利用

## 16. リリース完了条件

次のすべてを満たした時点でリリース完了とします。

- 対象のPull Requestが `main` にマージされている
- `main` がDocker環境で正常に動作する
- `vX.Y.Z` タグがGitHubへpushされている
- プラグイン内のバージョン情報が一致している
- 配布ZIPと更新JSONが公開されている
- releaseまたはhotfixブランチが削除されている

次回リリース予定は `3.9.0` です。
