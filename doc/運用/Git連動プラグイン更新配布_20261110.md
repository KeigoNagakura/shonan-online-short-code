# Git連動プラグイン更新配布

作成日: 2026-11-10 ／ 第1版

## 目的と構成

プラグイン用の非公開GitHubリポジトリ `KeigoNagakura/wp-plugin` のリリースタグを起点に、WordPressの通常の更新画面へ配布物を届ける。非公開リポジトリの認証情報を各WordPressサイトへ配らないため、ZIPと更新JSONは既存のHTTPS更新ホストで公開する。GitHub ReleaseはソースとZIPの履歴を残す場所として使う。

```text
main上の vX.Y.Z タグ
  → GitHub Actionsが構文・版を検査
  → Composer依存を含む so-short-code/ のZIPを生成
  → 更新ホストごとに同じホストのZIPを指すJSONを生成
  → SSHホスト鍵を検証してZIPを先に配置・ハッシュ確認
  → JSONを切り替え、GitHub Releaseを作成
  → WordPressが既存の更新機能で通知・取得
```

ワークフローは [plugin-update-release.yml](../../.github/workflows/plugin-update-release.yml)、ZIP生成は [build_update_package.py](../../scripts/build_update_package.py)、配置は [publish_update_package.py](../../scripts/publish_update_package.py) を使用する。タグのpushは配布を伴うため、[リリース運用](Gitブランチとリリース運用_20260927.md)の確認を終えてから行う。

## GitHub側で一度設定する項目

`plugin-updates` Environmentを作り、次の3つのEnvironment secretを設定する。値をGitや文書へ保存しない。

| secret | 内容 |
| --- | --- |
| `SOSC_DEPLOY_TARGETS` | 配布対象のJSON配列。各要素は `endpoint`、`ssh_host`、`ssh_user`、`directory`、任意の `ssh_port` |
| `SOSC_DEPLOY_SSH_KEY` | 配布専用SSH秘密鍵。公開先ディレクトリだけへ書けるアカウントを使用 |
| `SOSC_DEPLOY_KNOWN_HOSTS` | 接続先の確認済みSSHホスト公開鍵。接続時に取得した未確認値をそのまま信用しない |

対象設定の**形式例**（実際の接続情報ではない）:

```json
[
  {
    "endpoint": "https://api.shonan-online.com/out_source",
    "ssh_host": "ssh.example.invalid",
    "ssh_user": "plugin_deploy",
    "directory": "/srv/example-api/out_source",
    "ssh_port": 22
  }
]
```

`endpoint` はWordPressが取得する公開URL、`ssh_host` と `directory` はそのURLへ公開されるファイルの実配置先。公開URLとSSH接続先は同じ名前でなくてもよい。対象ディレクトリは先に作成し、配置アカウントに書込み権限を与える。ワークフローはディレクトリを作らない。

現行プラグインは `api.shonan-online.com` のJSONだけを見て、**ZIPも同じホストであることを検証する**。次回リリースで `sosys.shonan-online.com` に切り替える場合、旧版向けの `api` と新版向けの `sosys` を両方 `SOSC_DEPLOY_TARGETS` に登録し、それぞれに同じZIPとホスト別JSONを配る。旧版向けJSONから別ホストのZIPを指す構成は使えない。旧ホストの継続期間は[更新配信サーバー移行](更新配信サーバー移行_20260927.md)に従う。

## リリース前の確認

1. 変更をPRで検証して `main` にマージする。
2. `so_short_code.php` の `Version:`、`settings.php` の `SOSC_VERSION`、`update/so-short-code.json` の `version` をタグと一致させる。次回移行リリースでは `settings.php` の更新ホストも同時に変更する。
3. `SOSC_DEPLOY_TARGETS` に、プラグインが参照するホストと旧版のホストが含まれることを確認する。
4. 代表的な既存サイトと新規サイトで、更新前バックアップ、更新通知、ZIP取得、更新後の有効化・主要機能を確認する。SSH接続と公開URLの実確認がない状態でタグをpushしない。
5. 確認済みの `main` コミットに `vX.Y.Z` タグを作り、pushする。ワークフローが失敗した場合は、ZIP、JSON、GitHub Releaseのどこまで進んだか確認し、既存タグを付け替えない。

ビルドは `update/so-short-code.json` をZIPから除外する。ZIP内の古いハッシュ値との循環を避け、公開用JSONはビルド後の実ZIPハッシュから作る。ZIPルートは `so-short-code/` とする。同じリリースタグ・ソースで作ったZIPは同じSHA-256になる。

## 現在の状態

ローカルでZIP生成、2ホスト分のJSON生成、SHA-256再現性、配置設定の形式確認、GitHub Actions構文検査を実施した。**配布先のSSH接続情報と公開ディレクトリは未確認で、Environment secretは未設定**。そのため、現時点ではタグをpushしても自動配布を成功扱いにできない。サーバー設定と実接続の確認が残る。
