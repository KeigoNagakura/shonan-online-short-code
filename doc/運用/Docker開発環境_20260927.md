# Docker開発環境

- 初版: 2026-09-27、最終更新日: 2026-11-11
- 対象: `project/wp-plugin`のローカル開発専用
- 管理: [Compose](../../compose.yml)、共通起動Shell `C:\osaruAi\shell\WordPress開発環境_20260927.ps1`

## 起動・停止・ログイン

Docker Desktopを起動し、PowerShellから次を実行する。

```powershell
& C:/osaruAi/shell/WordPress開発環境_20260927.ps1 -ProjectRoot C:/osaruAi/project/wp-plugin -Mode Start
```

`Start`は設定検証、共通ローカルCAの初回信頼とwp-plugin専用TLS証明書の準備、イメージbuild、他のローカルComposeからの切替、DB・Web起動、Composer依存と指定プラグインの導入、ローカル管理者作成、URL整合、ログイン検証を行う。初期SQLがあれば空の新規DBボリュームへ読み込み、初期SQLがない新規環境ではWordPressを空DBへ初期構築する。再実行はDBを再投入せず、同じ管理者を保持する。`Stop`は対象サービスだけを停止し、ボリュームを保持する。

| 接続先・操作 | 値 |
| --- | --- |
| サイト | https://localhost/ |
| 管理画面 | https://localhost/wp-admin/ |
| phpMyAdmin | http://localhost:8080/ （wordpressユーザーで専用DBへ自動接続） |
| ユーザー名 | `wp_local_admin` |
| パスワード | 同じコマンドの`-Mode Password`でクリップボードへコピー |
| HTTPS証明書の信頼 | `Start`が共通CAを初回だけ登録。状態確認だけを行う場合は`-Mode Trust` |
| 確認 | `-Mode Verify` |
| 状態 | `-Mode Status` |
| 停止 | `-Mode Stop` |

パスワードは会話、README、履歴へ転記しない。クリップボードは使用後に消去する。HTTPSを正規URLとする。共通CAは同じPC・Windowsユーザーで初回だけ信頼し、以後のプロジェクト別leaf発行や更新では再登録しない。ブラウザを起動済みの場合、初回信頼登録後にブラウザを再起動する。

## 構成と保存先

Docker専用資材は`server/docker/`へ集約する。`server/`直下や他のサブディレクトリは実サーバーのデータ・差分などの用途とし、`.dockerignore`でDockerビルド対象から除外する。Compose定義はプロジェクト直下の`compose.yml`を使用する。

共通CAの秘密鍵はWindowsの`CurrentUser\My`証明書ストアへ非エクスポート可能として保存し、公開CAだけを`CurrentUser\Root`へ登録する。wp-plugin専用leafは`.local/tls`へ生成し、Apacheへ読み取り専用でmountする。別PC・別Windowsユーザーでは共通CAの作成・信頼を一度行う。詳細は基盤の[ローカル開発HTTPS証明書運用](../../../../doc/設計/ローカル開発HTTPS証明書運用_20261001.md)を参照する。

Compose名は`osaru-wp`。PHP 8.3/Apacheの公式WordPressイメージをdigest固定し、本体は手元のWordPress 7.0.3をコピーする。DBはMySQL 8.4.11。必要な拡張は起動後に検査する。TLS検証を無効化せず、Windowsの信頼済み公開証明書をbuild時に反映する。

自作プラグインの最低要件はPHP 8.2。現在のローカル環境に固定したContact Form 7はPHP 8.3以上を要求するため、全プラグインを同時に起動する通常の開発環境はPHP 8.3とする。

| 資材 | 保存・用途 |
| --- | --- |
| `osaru-wp_database` | 専用DB。`db/init/wordpress.sql`は空の新規ボリューム初期化時だけ実行 |
| `osaru-wp_wordpress` | 本体、外部プラグイン、uploads、バックアップなどの永続データ |
| `src/so-short-code` | 自作プラグインのbind mount。編集は即反映 |
| `.local/credentials.clixml` | Windows DPAPIで暗号化したDB・管理者・salt設定 |
| `.local/tls/localhost.crt` | 共通CA署名済みのwp-plugin専用公開証明書 |
| `.local/tls/localhost.key` | wp-plugin専用秘密鍵。現在のWindowsユーザー限定ACL、Git対象外 |
| `server/docker/local-ca.crt` | PCの公開信頼証明書群。起動時生成・Git対象外 |

認証情報は同じWindowsユーザー・PCでのみ復号できる。実行中のコンテナには環境変数で渡るため、Dockerの管理権限がある利用者からは参照可能。Docker inspectの環境変数をログへ出力しない。

phpMyAdmin 5.2.3はlocalhostの8080番だけへ公開し、専用DBのwordpressユーザーで自動接続する。root権限は渡さない。このPCから開いた画面でDBを編集できるため、共有公開には使用しない。Start/StopはphpMyAdminも対象とする。

元の`site/wp-config.php`、初期SQL、旧環境のDB・ボリュームは変更しない。新しい実行ボリューム内では、起動処理が管理するwp-config.phpと開発用MUプラグインだけを同期する。初期SQLがない別PCでは空の専用DBへWordPressを初期構築する。実データをGitで配布しない。

## 開発上の動作

- [固定プラグイン一覧](../../server/docker/required-plugins.json)の10件と自作プラグインを有効化する。固定版は現行ローカルWordPressの導入版と2026-11-11に照合した。既存ボリューム内の依存を変更する際は、新版の互換性確認と一覧更新を一体で行う。
- Composerはlockに従って自作プラグインの依存物を生成する。
- メールの外部送信、自動更新、アクセスによるWP-Cronは停止する。
- 自作プラグインの管理画面更新は拒否し、マウントしたソースを保護する。
- バックアップなどの定期タスクを確認する際は、対象と副作用を確認してWP-CLIから個別実行する。
- 定期処理と自動更新の状態だけを確認する場合は、[読取り診断](../../tests/runtime-schedule-check.php)を`wp eval-file`で実行する。ローカルではCronと自動更新が無効なのが正常で、期限超過の予約が表示されても本番の状態を示さない。
- PHPログは実行ボリュームの`wp-content/debug.log`。画面へのエラー表示は無効。
- バックアップ出力先と.zip.phpはGit除外。実行ボリューム内に保持する。

利用者のlocalhost接続指定に従い、新環境が80/443を使用する。WordPressのhome・siteurlは`https://localhost`へ統一する。HTTPは互換確認用として80番を維持する。旧配置のwp-plugin-devはDockerラベルで対象を確認して3コンテナを通常停止し、DB・volumeを保持した。旧環境を再起動するとポート競合するため、同時起動しない。旧Composeファイルは欠落しており、切替Shellでは復元できないため、今回の切替だけは確認済みコンテナ名を指定して停止した。新環境のDBポートはホストへ公開しない。

## データ保全・復旧

通常停止に`down -v`を使わない。DBボリュームがある状態で暗号化認証ファイルを作り直すと認証不一致になるため、`.local/credentials.clixml`を保持する。初期SQLにはDROP TABLEとユーザーデータが含まれる。稼働済みDBへ直接再投入しない。

WordPress本体は初期配置時にコピーするため、`site/`を変更してbuildしただけでは既存ボリュームの本体は更新されない。本体更新・DBリセット・別PCへの移行はバックアップと対象確認を伴う別作業とする。

## 検証範囲

`Verify`はDB接続、PHP拡張、固定プラグインの版・有効化、ショートコード登録、バックアップ保存先の書き込み、サイトURL、HTTPSログイン、プラグイン管理画面を確認する。決済・実メール送信・商品注文・帳票・バックアップの全回帰を保証するものではない。[移設前のテスト仕様](../検証/移設前のテスト仕様_20260927.md)に記載されたtestsやdockerディレクトリは未復元。
