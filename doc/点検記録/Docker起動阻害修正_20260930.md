# Docker起動阻害修正

## 結論

`wp-plugin`の初回Docker起動を妨げていた、初期SQLの必須化、旧プロジェクトパス、他Composeとのポート競合を修正した。構文、Compose設定、切替計画は検証済みである。実際の起動は`sosys`の停止と新規Dockerボリューム作成を伴うため、明示承認待ちとして未実施である。

## 障害情報

| 影響 | 現状のままではローカルWordPress環境を初回起動できない |
| 関連ブランチ | `feature/local-docker-and-documentation` |

## 再現条件

1. [Compose定義](../../compose.yml)を取得した新規環境で、`db/init/wordpress.sql`と既存の`osaru-wp_database`ボリュームが存在しない。
2. 共通起動Shell `C:\osaruAi\shell\WordPress開発環境_20260927.ps1`を`Start`で実行する。
3. 修正前は初期SQL欠落として停止する。
4. また、`sosys`がホストの80番・443番ポートを使用中の場合、直接`docker compose up`するとポートが競合する。

## 根本原因

- 初期SQLはGit管理外である一方、起動Shellが初回起動に必須としており、新規cloneだけでは前提を満たせなかった。
- 起動Shellが共通のCompose切替処理を通さず、固定ポートを使用する別プロジェクトとの排他を実施していなかった。
- READMEと運用書のコマンドが旧パス`project/wp`を参照していた。

## 見逃し理由

- `docker compose config`の検証だけでは、Git管理外の初期SQL欠落と実行時のポート競合を検出できなかった。
- Docker資材を含むブランチを反映した時点で、起動Shellが参照する外部資材と稼働中Composeまで確認していなかった。

## 修正

- 初期SQLがない新規環境では、空の専用DBへWordPressを初期インストールする分岐を追加した。
- 初期SQLが存在するのにWordPressが未導入の場合は、既存データを上書きせず停止する保護を追加した。
- `Start`で共通Docker Compose切替起動Shell `C:\osaruAi\shell\DockerCompose切替起動_20260926.ps1`を呼び、対象外Composeをボリューム保持で停止してから起動するよう変更した。
- [README](../../README.md)と[Docker運用書](../運用/Docker開発環境_20260927.md)の対象パスと初回起動手順を更新した。
- 共通のShell一覧へ変更後の挙動を反映した。

## 恒久対策

- 起動Shell内で対象Compose名、ローカルDocker endpoint、必須ファイルを継続して検証する。
- 初回DBは「初期SQLから復元」と「空DBへ新規構築」を明示的に分岐し、既存ボリュームは再初期化しない。
- ポート切替は共通Shellへ一本化し、失敗時の元Compose復元機構を利用する。
- Docker資材の反映確認では、Compose構文だけでなく、Git管理外の入力、稼働中Compose、公開ポートを確認する。
